## Two defects found and fixed during implementation

Both were found by writing the test, not by reading the code.

1. **`ON DUPLICATE KEY UPDATE` assignment order** (`db.go admitMemberTx`). MySQL evaluates
   those assignments left to right, and a column read on the right sees the value written by
   a preceding assignment. `updated_at = IF(status = 0, …)` sat AFTER `status = 1`, so the
   condition was permanently false and re-admitting a removed member kept the `updated_at`
   from when they were removed — "when did this seat come back" was silently unanswerable.
   Reproduced both ways on MySQL 8.0.33 in a scratch database before fixing. Pinned by
   `TestReactivationResetsRoleAndTimestamps`.

2. **`c.BindJSON` writes the response itself.** gin's `BindJSON` calls
   `AbortWithError(400)`, which emits the 400 header before the handler can respond; the
   envelope then lands under a status gin chose. On the `leave` endpoint, where an empty body
   is the NORMAL case, that pinned every ordinary leave to a 400 header with a 200 body. The
   whole module now binds with `ShouldBindJSON`. This is latent across the repo's 221 other
   `c.BindJSON` sites — invisible today only because `ResponseErrorL` also pins the wire
   status to 400 (D5) — but it is not this task's to fix, and it would bite the moment a
   module moved to `ResponseErrorLWithStatus`.

## Acceptance items NOT met, and why

- **Invite-code items** (anonymous preview, `POST /v1/projects/join`, concurrent
  `max_uses = 1` consumption, 7-day expiry, one generic code for
  invalid/expired/revoked/exhausted, `StrictIPRateLimitMiddleware("project_invite")`,
  "orphaned invitations" in the reconcile scan). Deferred to **P2** at the requester's
  direction, together with the `octo_project_invitation` table. P0 therefore ships **two**
  tables, and the only admission path is owner/admin direct-add. The I1 acceptance item
  "rejected on both the direct-add path and the invite-accept path" is met on the half that
  exists.
- **`member_epoch` monotonicity as a reconcile check.** Cannot be done as specified: a
  read-only scan that runs on every pod would have to remember the previous value, and an
  observed "regression" could just be two replicas reading either side of one increment. The
  guarantee is instead the write discipline — every statement is `member_epoch =
  member_epoch + 1`, never an absolute assignment — enforced by
  `TestMemberEpochOnlyEverIncrements`. The scan keeps a negative-value sentinel and a
  process-local best-effort regression counter, labelled as best-effort in the code.
- **A queryable audit trail.** This repo's only audit precedent is structured zap output
  (`modules/messages_search/audit.go`); there is no audit table in the schema. Audit entries
  are emitted through an injectable sink so the "every write path audits the actor, the
  target and the reason" contract is asserted (`TestEveryWritePathEmitsAnAuditEntry`,
  `TestCascadeEmitsAnAuditEntry`). If the product needs audit **search**, that is a new
  table and its own task.

## Must be checked before merge — cannot be verified from here

# Code review pass (2026-09-04, after implementation)

Reviewed the full diff for security and quality. **0 CRITICAL, 3 HIGH, 3 MEDIUM.** All HIGH
and two MEDIUM are fixed with regression tests in `modules/project/review_fixes_test.go`;
each of those tests fails against the code as originally written.

## Security: clean

- **No secrets in non-test code.** The only credentials anywhere are in `_test.go`: the
  `root:demo@tcp(127.0.0.1)/test` DSN that octo-lib's own `testutil.NewTestServer` hardcodes,
  and the 32-char `OCTO_MASTER_KEY` fallback used identically by `modules/space` and
  `modules/bot_provision`.
- **No SQL injection.** Every value is a bound parameter. There are exactly two places where
  anything non-literal reaches a query, and both were checked: `listVisibleInSpace` switches
  between two *code-constant* fragments, and `updateProfileTx`'s column names come from a
  six-entry allow-list built in `updateProject`, never from the request payload.
- **No XSS / template injection surface** — JSON responses only, no HTML rendering.
- **No path traversal** — no request input reaches a filesystem path. `time.LoadLocation` is
  the only name-to-resource lookup, it is env-sourced (operator, not user), and Go rejects
  `..` and absolute names itself.
- **Every route is behind `AuthMiddleware`**, asserted structurally, and P0 mounts no
  unauthenticated route.

## HIGH-1 — the Space-removal cascade silently abandoned seats past the first page

`cleanupSpaceMemberProjects` processed one 200-row page and returned `nil`. The worker then
marked the job `done`, and **nothing re-drives a done job** — the reconcile scan is read-only
by design (D7), so it only ever reports. A member with more than one page of seats in one
Space kept every seat past the first, permanently. The per-Space project quota is 1000, so
this was reachable, and the code comment asserting "the reconcile job is the backstop" was
simply wrong about what reconcile does.

Fixed: loop until a short page comes back; if the page budget runs out, confirm a seat really
remains and return a retryable sentinel so the job is re-claimed. Each pass makes progress
(closed seats stop matching the status filter), so retries converge instead of spinning.

**A bug in that fix was then caught by an existing test.** The first version defaulted the
"budget spent" flag to `true` and relied on each `break` to clear it — the `len == 0` break
did not, so a removed member with *no* project seats got a retryable error. That is the
majority of removals, and it would have burned the shared job's entire retry budget on every
one of them, pushing jobs to `abandoned` and degrading the group cascade for everybody.
`TestCascadeIsNoOpWithNothingToDo` failed immediately; the flag now starts `false`.

Related fix in the same path: a stale active seat on a *disbanded* project used to be skipped
("nothing to do"), which both left an I1 violation the scan would report forever and made the
paging loop read "no progress" and stop. It is now closed, without an epoch bump.

## HIGH-2 — data race in the reconcile worker, plus no reentrancy guard

`scanEpochSanity` reset its history with `lastSeenEpoch = sync.Map{}`. That is a race twice
over: an unsynchronised write to a shared package variable, and copying a struct that contains
a Mutex. It was reachable because `config.Context.Schedule` is backed by a timing wheel that
fires `go task()` on every tick **without waiting for the previous run**
(`timingwheel.go:117`), so any scan slower than its interval overlaps itself. `-race` did not
catch it because the tests only ever called `runReconcile` once, synchronously.

Fixed: `epochHistory`, a mutex-guarded map with bounded capacity, plus `atomic.Bool`
reentrancy guards on both `runReconcile` and `refreshDistributionMetrics` — the same guard
`modules/space` puts on its own worker, for the same documented reason.

## HIGH-3 — the I1 check ran outside the write transaction, while the comment claimed otherwise

`addOneMember` called `pkg/space.CheckMembership`, which takes a `*dbr.Session` and therefore
runs on a **different pooled connection in its own implicit transaction**. The comment above
it opened with "I1, inside the transaction" and then admitted the read was not on `tx`,
justifying it with "a snapshot read is sufficient" — a claim the code does not support. A
Space removal committing between that read and our commit produced a project seat with no
Space seat; only the asynchronous cascade closed it. The brief requires the check to be inside
the request transaction precisely so that window does not exist.

Fixed: `checkSpaceMembershipForWriteTx` runs the identical predicate on `tx` with
`FOR SHARE OF sm`, so a concurrent Space removal (which takes `FOR UPDATE` on the same row)
blocks until we commit. Taken **before** the `octo_project` lock so the module's declared lock
order (space → project → … → octo_project_member) still holds; the cascade reads
`space_member` without a lock, so there is no cycle. `FOR SHARE OF` needs MySQL 8.0.1+ and was
verified on 8.0.33. The test asserts the serialization directly: while the check's transaction
is open, an `UPDATE space_member` on a separate connection with a 1s lock timeout gets 1205,
and succeeds again after rollback.

## MEDIUM-1 (fixed) — privilege TOCTOU: the actor's role was never re-read under lock

`removeMember` / `changeMemberRole` / `addOneMember` trusted the role `projectMiddleware`
resolved — which came from the Redis membership cache, read before the transaction opened.
`modules/space` deliberately re-reads the operator role in-lock for the same operation, with
the reason recorded at `modules/space/api.go:871` (PR #339 review); this code diverged from
that without saying so. `actorUID` was additionally accepted by `changeMemberRole` and **never
read** — an unused parameter on an authorization-relevant function, which reads exactly like a
check that was intended and dropped. (`unparam` is disabled in this repo's `.golangci.yml`, so
no linter would have said so.)

Fixed: `actorRoleTx` re-reads the actor's own seat under the project lock, and all three write
paths enforce against that. The handler-level checks stay as cheap pre-checks so an
unauthorized batch does not open a transaction per uid.

**That fix surfaced a wire-contract problem worth its own note.** With the in-lock check in
place, an actor who had lost their role got HTTP 200 with a per-uid `permission_denied` — the
batch handler mapped one sentinel to a per-target outcome. That reports a *complete*
authorization failure as a success. The sentinel is now split: `errPermissionDenied`
(actor-level → one top-level 403, stop the batch) versus `errTargetProtected` /
`errSelfRemovalNotAllowed` (target-level → per-uid). The client-visible reason string is
unchanged, so no client has to learn a new value.

## MEDIUM-2 (fixed) — `?page=…` overflowed into a user-triggerable 5xx

`(page-1)*limit` with `page=9223372036854775807` overflowed to a negative `OFFSET`, which
MySQL rejects with 1064, so the handler answered `err.server.project.query_failed`
(`Internal`, `http_status` 500). Any Space member could turn a query parameter into a 5xx plus
a stream of internal-error logs — self-serve alert noise. Reproduced end to end before fixing.
`page` is now clamped, so a page past the end is an empty page, which is what every other list
endpoint here returns.

## MEDIUM-3 (accepted, not changed) — 13 functions over 50 lines; one nesting depth of 6

The long functions are handlers and transaction bodies whose length is validate-then-call
sequences and explicit error mapping; the surrounding modules (`space`, `group`) are written
the same way, and splitting them would add indirection and churn without reducing risk.
`scanEpochSanity` reaches depth 6 in one nested-`if` inside two loops. Recorded rather than
silently "fixed", so the next reader knows it was a decision.

## LOW (noted, not changed)

- `updateProfileTx` iterates a map, so the `SET` clause order is nondeterministic and the
  prepared-statement cache sees N variants. No clause reads another column, so it is correct.
- `queryIsOfficialFlags` / `officialFlagModel` are production code used only by the D6 test.
  That is the mechanism the acceptance criterion asks for, so it stays.
- `⚠️` appears in two comments and the migration. Matches existing repo style
  (`modules/group/space_member_removal.go`).

## P1-1：reconcile cursor 每 tick 重置，超过 25,000 行后永久漏扫

后果是这些扫描**只可能看到前 `reconcileMaxPages × ReconcileLimit` 行**（默认 25,000）。再往后
的行永远不被检查——一个 id 更大的项目可以长期处于违约状态而没有任何一轮会看它。

而我在那个常量上写的注释是「the next tick continues from a fresh cursor」。这是本任务里
**第三次**出现同一类缺陷：注释断言了代码不具备的性质。

修复：新增 `reconcileCursors`，cursor 跨 tick 持久化，扫到表尾（短页）时归零重新轮转，
即 notify welcome ledger 的 "cursor rotation under a shared budget" 形状。

连带修一个 reviewer 未提但由此暴露的问题：**gauge 的语义**。若一 tick 只覆盖部分键空间，
`Set` 上去的是偏小的数，告警阈值永远不会触发。所以每个 rotation 现在跨 tick 累加，
**只在一轮完整走完时才 publish**。

## P1-2：直接提升角色未复核 Space 成员身份

`promoteSuccessorTx`（转让路径）已有校验，但**直接** role change 走的是另一条门：直接
`updateMemberRoleTx`。后果正是转让路径当初被加固时要防的那个终局——把一个 Space 席位已被移除、
级联尚未追上的成员提为 owner，owner 数变 2，原 owner 于是可以无转让退出，级联随后关掉新 owner，
项目无人可管理。

修复：`role > target.Role && role >= RoleAdmin` 时在同一事务内校验目标的 Space 席位。
**只拦提升**——降级是收权，因为目标即将离开就拒绝它，反而会挡住运维做那件安全的事。

## P2-3：新 pending 工单存在时，旧 abandoned 工单仍误报

`remove → rejoin → remove` 会入队第二条工单（outbox 刻意不对 `(space_id, uid)` 唯一），
所以一个 pair 可以同时挂着一条旧 abandoned 和一条在途 pending。旧实现只看 abandoned，
把「已经排好队的工作」报成「无自动重驱动、需人工介入」。修复：加 `NOT EXISTS` 排除有 pending
工单的 pair——与 I1 扫描已有的在途豁免同一口径。

## P2-4：leave 吞掉畸形 JSON，可能意外退出项目

`_ = c.ShouldBindJSON(&req)` 吞掉全部错误。截断或语法错误的 body 会被解析成空结构体，
于是 `transfer_to` 静默变成 `""`，成员照样退出了项目。**一个破坏性动作不该是坏 payload 的
失败模式。** 修复：只容忍 `io.EOF`（本路由空 body 是正常情况），其余绑定错误返回
`request_invalid`。测试覆盖三种畸形 body + 空 body + `{}`。

## P2-5：owner 转让未记录继任者

leave 带转让、以及降级最后一个 owner，都在同一事务里提拔了继任者，但审计只记了「原 owner 离开」
或「某人被降级」。日志因此无法回答交接后**谁掌握了这个项目**——恰恰是一次所有权交接最需要留下的
那个事实。修复：`leaveProject` / `changeMemberRole` 返回 successor，handler 为其补一条
`project.role_change` 审计（reason 区分 `ownership_transferred_on_leave` /
`_on_demote`）。

## P2-6：批处理中途降权，已部分提交却返回整体 403

每个目标一个事务，所以 actor 在批次中途失去权限时，前面的目标已经**持久提交**。旧实现丢弃已
收集的 outcomes、返回一个裸 403，等于告诉调用方「什么都没发生」而数据库不同意——而且客户端重试
整批会把成功的那部分**再执行一次**。

修复：区分两种情形。**一条都没提交**时，单一状态码仍是最诚实的答案（保持 403/404）；
**已有提交**时返回 200 + 完整 per-target outcomes，并把没走到的目标标为 `not_attempted`，
让调用方能把「被拒」和「没试」分开、只重试后者。add 与 remove 两条批处理路径同样处理。

## 关于 reviewer 报告的「测试被迁移冲突阻断」

reviewer 那侧 `event 表已存在`、用例未真正执行。这是**本地测试库前置条件**，不是代码问题：
`testutil.NewTestServer` 以 `Migration=false` 连共享 `test` 库，而 sql-migrate 的迁移账本
按包变化，跨包复用同一个库就会 `unknown migration` / 表已存在。CI 靠 `ci/run-e2e-shard.sh`
**每个包之前 DROP/CREATE `test` 库**来规避。

# 第四轮 review：1 条 P2 修复（2026-09-06）

**addMembers 先跑完整个批次，handler 却把首个权限错误之后的结果标为 not_attempted** ——
核实属实，已修。

## 问题

两条批处理路径的执行模型不同，但 `not_attempted` 这个标签只对其中一条成立：

- **remove**：handler 驱动、逐目标执行，遇到 actor 级失败就停 —— 终止点之后的目标
  **真的没被尝试**，`not_attempted` 是事实。
- **add**：`service.addMembers` **无条件跑完整个批次**（每个目标一个事务），handler 事后
  才遍历 results，在 `results[i+1:]` 上打 `not_attempted` —— 而那些目标**已经被执行过**，
  其中一些已经成功提交。

三个后果：一个已提交的添加被报成「从未尝试」；它的审计条目（handler 逐 outcome 发）随之
丢失；同一个标签在 remove 路径是真话、在 add 路径是谎话。调用方若相信这个报告去重试，
会把已提交的部分再执行一遍。

## 修复

**终止发生在 service 层，而不是 handler。** `addMembers` 在第一个 actor/project 级失败
（`errPermissionDenied` / `errProjectGone`）时 break —— 后续每个目标都只会开一个事务然后被
in-lock 复核拒绝，继续跑纯属浪费。handler 相应改用 `uids[len(results):]` 标注未执行部分
（`results[i+1:]` 在此处为空，会让那些 uid 从响应里彻底消失）。

这样「权限中途恢复」的窗口不复存在：第一个失败之后批次已经停止，不存在「后续已提交却被
误报」的目标。两条路径的 `not_attempted` 现在都精确指向「执行真正停止的地方」。

## 测试

`TestAddBatchStopsAtActorLevelFailureAndLabelsOnlyTheTail`：a1 成功提交、a2 被 seam 拒绝
（模拟 actor 权限过期）、a3 未被触碰。断言：响应 200 且三个 uid 各出现恰好一次
（ok / permission_denied / not_attempted）；**seam 调用计数为 2**（批次真的停了）；a3 在
数据库中没有席位（不是没报，是真的没跑）；审计有 a1、无 a3。
