# 变异必须由不知道测试怎么写的人来选

## 观察到的事

一个分支交付时声称「每条测试都做了变异验证」。那不是假话——变异确实跑了，也确实
看到了红。但变异是**测试作者自己挑的**，于是挑中的永远是测试抓得住的那个。

随后的对抗式审查用不同的变异重跑同一批测试，两条守卫塌了，而且是**两个方向都错**：

| 测试 | 变异 | 结果 |
|---|---|---|
| 源码守卫（禁止放宽鉴权谓词） | 把谓词放宽成 `(status = 1 OR status = 2)`——**正是它声称要拦的安全回归** | **PASS** |
| 同上 | 把 `s.status = 1` 写成 `s.status=1`（纯格式） | **FAIL** |
| 错误分支断言 | 删掉「两条路都失败」分支 | **PASS** |

第一条最能说明问题：作者用 `<> 0` 做变异，而那条守卫恰好 grep 这个字符串。
**自己给自己出题，出的永远是自己会做的题。**

## 为什么会这样

变异验证的价值在于「测试与实现之间是否真的存在耦合」。但作者对实现有一份心智模型，
挑变异时会不自觉地挑那份模型里「最像 bug」的改动——而测试也是照同一份模型写的。
两者共享同一个盲区。

源码文本断言（grep 实现文件）尤其危险：它把耦合建立在**拼写**上而不是**行为**上，
于是同时具备「无害改动会误报」和「真回归能溜过」两种性质。

## 做法

1. **变异不要自己挑。** 交给不知道测试怎么写的人 / 视角；或者机械地选「最像真实
   回归的那个改动」——通常就是把加固过的判断改回加固之前的样子。
2. **优先行为断言，而不是源码文本断言。** 想钉住「两个谓词必须保持不同」，就在同一
   批种子数据上同时问两个谓词、断言它们在关键那一格分道扬镳；不要 grep 源码。
   前者对格式免疫，对语义敏感；后者反过来。
3. **断言要落在能区分两种情形的那一半上。** 例中两条错误信息都含 `fallback`，
   断 `fallback` 等于什么都没断；要断 `also failed`。
4. **声称「已做变异验证」时，写清楚变异是谁挑的。** 「我改了 X，测试变红」和
   「一个不知道测试内容的评审改了 X，测试变红」不是同一强度的证据。

## 建议提升为规则的部分

`testing` 规则里可以加一条:凡是以「守卫 / guard」为名的测试,必须给出**至少两个**
变异的结果——一个是它声称要拦的真回归,一个是应当放行的无害改动。只给前者不够,
因为过紧的守卫会在无害改动上误报,最终被人删掉或加豁免,守卫也就名存实亡。
