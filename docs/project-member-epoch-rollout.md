# `member_epoch` 起点为 1 的上线与回滚说明

`octo_project.member_epoch` 是给外部控制面用的**变更检测器**：对端把一次授权判定
缓存起来，并以 epoch 为键，之后再读一次 epoch 来判断缓存是否还有效。

集成契约把 **0 定义为「项目不存在或不可见」**。因此 0 必须是一个**活跃项目取不到的值**，
否则一个刚建好的项目和一个已解散的项目会给出同一个答案——对端的过期检查会「同意」，
被缓存的授权就永远不会失效。

本文档说明为保证这一点做了什么，以及上线/回滚时运维需要知道的事。

## 1. 三个写入方，两个是一次性的

| 机制 | 触发时机 | 覆盖范围 |
|---|---|---|
| 建项目时 `bumpMemberEpochTx` | 每次创建 | 新二进制创建的项目从 1 开始 |
| 迁移 `20260908000001` 回填 | 每个部署启动执行一次（记账在 `gorp_migrations`） | 已存在的 0 值行，一次性抬到 1 |
| 对账扫描 `repairAbsentSentinelEpoch` | 每轮对账（`scanEpochSanity`，不受 `OCTO_PROJECT_RECONCILE_ENABLED` 门控） | **持续**修复重新落回 0 的活跃项目 |
| **读取层拒绝** `ErrLiveProjectOnAbsentSentinel` | 每次请求 | 发现活跃项目落在 0 上就**拒绝服务**（500），绝不把哨兵值发出去 |

前三个都是一次性或定时的，只有第四个在每次请求上生效——它才是端点 fail-closed
推理真正依赖的东西。

## 2. 滚动发布期间会出现 0 值行，端点会拒绝而不是照发

回填在第一个新 pod 启动时就执行了，而此时旧镜像的 pod 仍在按列默认值 0 插入项目。

**本文档之前把这个残留写成了「只是可用性方向」，那是错的。** 如果把这样的行照常发出去，
陈旧授权方向同样可达，而且一旦发生就是永久的：

1. 旧 pod 建出项目 P：`member_epoch = 0, status = 1`；
2. 对端 verify，被告知「是成员，epoch 0」，于是按 `0` 缓存了一个肯定授权；
3. 对账扫描还没轮到 P，P 就被解散了——解散是**先 bump epoch 再翻 status**，行变成
   `epoch = 1, status = 0`；
4. 对端重新读 epoch：`status = 1` 过滤把 P 丢掉，返回 0；
5. `0 == 0`，过期检查**通过**，授权永不失效。

而且修复扫描事后救不回来：它的谓词要求 `status = 1`，第 3 步之后这行永远不匹配。

所以读取层直接拒绝：活跃项目落在 0 上时，两个端点都返回 **500**，对端重试，
对账扫描在一轮之内把行修好，服务自动恢复。窗口的代价从「永久授权」变成了
「一段可用性」——这是本模块在其它每一处都选的方向。

**注意影响面：拒绝是按请求而不是按项目的。** 对端一次最多批量查 50 个 id，只要这批里
有一个是 0 值行，**整批**都返回 500。所以运维看到 500 尖峰时，波及的项目数会明显多于
真正处于 0 值的项目数——这是预期行为（响应里没有逐项报错的通道，漏掉那一项就等于又把
哨兵值从「键缺失」这条路发出去了），不要往数据库故障方向排查。

无需人工操作。日志里会有一条专门的 ERROR（带 `projectId`）说明正在拒绝的原因。
若要缩短窗口，可采用 expand/contract 顺序：先只发建项目路径的 bump，等滚动完成后
再上迁移。

## 3. 回滚：**必须保持对账在跑**

迁移的 Down 段是 no-op，账本行也会保留。所以：

- 回滚二进制后，**旧的建项目路径会重新按 0 插入**；
- 再前滚时，迁移**不会重跑**（账本认为已应用）。

这是回滚方向需要注意的事：**回滚后不要同时关掉对账循环**。扫描会在每轮把这些行
修复掉，并按异常计数（`epochAnomalies`）报警——报警在这里是正确行为，它说明「还有实例
在按旧逻辑写 0」。

不过这已经不是**安全**前提，只是可用性前提了：即使对账循环被关掉，读取层也会拒绝
服务这些行（见第 1 节第四条），不会把哨兵值发给对端。关掉循环的后果是这些项目对
Loop 侧一直不可用，而不是被错误授权。

回滚期间的预期副作用：**每个受影响项目会有一次 epoch 提升**，对端因此会多做一次
重新校验。这是安全方向的代价。

## 4. 回填语句的操作影响

`UPDATE octo_project SET member_epoch = member_epoch + 1 WHERE member_epoch = 0`
没有支撑索引，在存量部署上会匹配大部分行，并在**每个 pod 启动时同步执行一次**
（后续 pod 因账本记录而跳过）。

在大表上这意味着首个 pod 的就绪延迟、行锁与主从延迟。**锁的范围是整表**：`member_epoch`
上没有索引，InnoDB 会扫描并锁住它扫过的每一行，直到语句结束——也就是说这期间
`octo_project` 上的并发写会被阻塞，而不只是那些 0 值行。

表规模较大的部署建议在低峰期执行首次升级；语句本身是幂等的（跑完之后谓词不再匹配任何
行），Down 是 no-op，所以中断后重启是安全的。多个 pod 同时启动也安全：语句自带的谓词
就是它的 CAS，后到的那个匹配 0 行。

对账扫描里的修复语句不受影响——它按 `project_id` 定位单行。

## 5. Space 轴：哪些变化会移动 epoch，哪些不会

对端把 epoch 一致当作「缓存仍然有效」的判据。这里逐条写清楚哪些事件会让它变，因为
**漏掉任何一条，都等于对端拿着一个它自己检查不出过期的授权**。

| 变化 | epoch 会动吗 | 机制 |
|---|---|---|
| 项目成员增删 / 改角色 | ✅ 同事务内 +1 | 写路径直接 bump |
| 项目解散 | ✅ | 先 bump 再翻 status；随后它从 epochs 结果里掉出，读作 `0` |
| **Space 封禁 / 解封** | ✅ | 不写项目行，但 epochs 的谓词会把父 Space 不活跃的项目折成 `0`；解封后恢复原值 |
| **Space 解散** | ✅ | 同上。注意本仓**不会**级联解散其下项目，它们的 `status` 永远是 1——全靠这条谓词 |
| **Space 成员移除** | ✅ **同事务内 +1** | 见下 |

### Space 成员移除为什么必须在事务内 bump

移除该成员的项目席位是**异步**的：移除事务只写一条清理工单，真正关席位的作业可能在
退避里待上几分钟，而且**重试 20 次耗尽后进 abandoned 终态，不再被任何东西认领**。

如果 epoch 等到关席位时才动，那么在这段时间里：`_verify` 已经答 `member:false`
（它会合取 Space 成员资格），而 `epochs` 还答旧值——对端重读 epoch 拿到同一个数，
**过期检查通过，被撤销的授权继续有效**。正常路径上是几分钟，作业 abandoned 之后是永久。

所以移除事务内会执行一条语句，把该成员还持有席位的所有活跃项目的 `member_epoch` 一次性
+1。**这条语句失败会让整次成员移除回滚**——宁可让调用方重试，也不要提交一次没有失效
信号的移除。

### 运维注意

- 一次移除会让该成员所在的**每个**项目的 epoch +1，对端因此对这些项目各多做一次重新
  校验。这是必要代价。
- 兜底告警 `scanAbandonedCleanupLeak`（「Space 成员移除工单已 abandoned，项目席位仍活跃」）
  在 `OCTO_PROJECT_RECONCILE_ENABLED` 门内，而该开关**默认关闭**。席位泄漏本身现在不再
  影响授权正确性（epoch 已经在移除时动过了），但它仍是需要人工介入的状态——**建议开启**。

## 6. 监控

- `epochAnomalies`：负值、同副本回退，以及**活跃项目落在 0 上并被修复**三类合一。
  上线完成后这个计数应当归零；持续增长意味着仍有按旧逻辑写入的实例。
- 修复日志：`活跃项目的 member_epoch 落在契约保留的 0 上，已提升为 1`，带 `projectId`。
  单轮条数受 `reconcileLogCap` 限制，总数进 gauge。
