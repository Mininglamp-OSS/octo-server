# `member_epoch` 起点为 1 的上线与回滚说明

`octo_project.member_epoch` 是给外部控制面用的**变更检测器**：对端把一次授权判定
缓存起来，并以 epoch 为键，之后再读一次 epoch 来判断缓存是否还有效。

集成契约把 **0 定义为「项目不存在或不可见」**。因此 0 必须是一个**活跃项目取不到的值**，
否则一个刚建好的项目和一个已解散的项目会给出同一个答案——对端的过期检查会「同意」，
被缓存的授权就永远不会失效。

本文档说明为保证这一点做了什么，以及上线/回滚时运维需要知道的事。

## 1. 四个写入方 + 一道读取层拒绝

| 机制 | 触发时机 | 覆盖范围 |
|---|---|---|
| 建项目时 `bumpMemberEpochTx` | 每次创建 | 新二进制创建的项目从 1 开始 |
| 迁移 `20260908000002` 回填 | 每个部署启动执行一次（记账在 `gorp_migrations`） | 已存在的 0 值行，一次性抬到 1 |
| 对账扫描 `repairAbsentSentinelEpoch` | 每轮对账（`scanEpochSanity`，不受 `OCTO_PROJECT_RECONCILE_ENABLED` 门控） | **兜底**修复重新落回 0 的活跃项目；受游标进度限制，见第 2 节 |
| **请求触发的带外修复** `RepairAbsentSentinelEpoch` | 每次撞上哨兵值的请求（`modules/internal_membership` 拒绝后异步执行） | **真正决定恢复时间的就是这一条**：命中的那一行当场抬起来，对端重试即成功 |
| **读取层拒绝** `ErrLiveProjectOnAbsentSentinel` | 每次请求 | 发现活跃项目落在 0 上就**拒绝服务**（500），绝不把哨兵值发出去 |

前两个是一次性的，第三个是定时的；只有后两个在每次请求上生效——读取层拒绝是端点
fail-closed 推理真正依赖的东西，带外修复是恢复时间真正依赖的东西。

> 这张表此前只列了前三项加读取层拒绝，恢复时间的说法因此建立在对账扫描上，而那是错的
> （见第 2 节）。带外修复是第五个机制，补进来的原因就是它。

## 2. 滚动发布期间会出现 0 值行，端点会拒绝而不是照发

回填在第一个新 pod 启动时就执行了，而此时旧镜像的 pod 仍在按列默认值 0 插入项目。

**本文档之前把这个残留写成了「只是可用性方向」，那是错的。** 如果把这样的行照常发出去，
陈旧授权方向同样可达，而且一旦发生就是永久的：

1. 旧 pod 建出项目 P：`member_epoch = 0, status = 1`；
2. 对端 verify，被告知「是成员，epoch 0」，于是按 `0` 缓存了一个肯定授权；
3. 对账扫描还没轮到 P，P 就被解散了——解散是**先 bump epoch 再翻 status**，行变成
   `epoch = 1, status = 0`；
4. 对端重新读 epoch：`status = 1` 过滤把 P 丢掉，返回 0；
5. `0 == 0`，过期检查**通过**，授权永不失效。

而且修复扫描事后救不回来：它的谓词要求 `status = 1`，第 3 步之后这行永远不匹配。

所以读取层直接拒绝：活跃项目落在 0 上时，两个端点都返回 **500**。窗口的代价从
「永久授权」变成了「一段可用性」——这是本模块在其它每一处都选的方向。

**这段窗口有多长。** 端点在拒绝的同时会把那一行**带外修复**掉
（`RepairAbsentSentinelEpoch`，异步、不占请求路径），所以实际上是**一次请求**。

**不要按「对账扫描一轮之内修好」来估**——那是本文档此前的说法，是错的。
`scanEpochSanity` 每 tick 只走有限页数，且游标是**持久化**的；未升级 pod 插入的行 id 最大，
要等游标跑完当前一整轮才轮得到。`octo_project` 大表上这是**小时级**。加上下面这条
按批拒绝的性质，只靠扫描兜底的窗口会显著超出一个对账周期。

**注意影响面：拒绝是按请求而不是按项目的。** 对端一次最多批量查 50 个 id，只要这批里
有一个是 0 值行，**整批**都返回 500。所以运维看到 500 尖峰时，波及的项目数会明显多于
真正处于 0 值的项目数——这是预期行为（响应里没有逐项报错的通道，漏掉那一项就等于又把
哨兵值从「键缺失」这条路发出去了），不要往数据库故障方向排查。

无需人工操作。日志里会有一条专门的 ERROR（带 `projectId`）说明正在拒绝的原因。
若要缩短窗口，可采用 expand/contract 顺序：先只发建项目路径的 bump，等滚动完成后
再上迁移。

## 3. 回滚：**必须保持对账在跑**

迁移的 Down 段是 no-op，账本行也会保留。所以：

- 回滚二进制后，**旧的建项目路径会重新按 0 插入**；
- 再前滚时，迁移**不会重跑**（账本认为已应用）。

这是回滚方向需要注意的事：**回滚后不要同时关掉对账循环**。扫描会持续修复这些行，
并计入 `project_member_epoch_anomalies_total`（Prometheus **Counter**）——计数在这里
上涨是正确行为，它说明「还有实例在按旧逻辑写 0」。

**恢复时间按「一次请求」估，不要按「一轮对账」估。** 对端查到哪一行，哪一行就被带外
修复（第 1 节第四条）；没人查到的行才等扫描，而扫描要等游标走到，大表上是**小时级**，
不是一个对账周期。规划回滚窗口时按后者算会低估——而且拒绝是**按批**的（见下），
受影响的项目数会明显多于真正落在 0 上的项目数。

不过这已经不是**安全**前提，只是可用性前提了：即使对账循环被关掉，读取层也会拒绝
服务这些行（见第 1 节第四条），不会把哨兵值发给对端。关掉循环的后果是这些项目对
Loop 侧一直不可用，而不是被错误授权。

回滚期间的预期副作用：**每个受影响项目会有一次 epoch 提升**，对端因此会多做一次
重新校验。这是安全方向的代价。

## 4. 回填语句的操作影响

`UPDATE octo_project SET member_epoch = member_epoch + 1 WHERE member_epoch = 0`
没有支撑索引，在存量部署上会匹配大部分行，并在**每个 pod 启动时同步执行一次**
（后续 pod 因账本记录而跳过）。

在大表上这意味着首个 pod 的就绪延迟、行锁与主从延迟。**锁的范围是整表**：`member_epoch`
上没有索引，InnoDB 会扫描并锁住它扫过的每一行，直到语句结束——也就是说这期间
`octo_project` 上的并发写会被阻塞，而不只是那些 0 值行。

表规模较大的部署建议在低峰期执行首次升级；语句本身是幂等的（跑完之后谓词不再匹配任何
行），Down 是 no-op，所以中断后重启是安全的。

⚠️ **但多个 pod 同时启动并不安全，这一条此前写错了。** 「后到的那个匹配 0 行」只在
先到的那个**已经提交**之后成立。若 pod B 在 pod A 还在执行那条整表 UPDATE 期间启动，
B 的同一条语句是**当前读**，会阻塞在上一段说的那批整表行锁上；到
`innodb_lock_wait_timeout`（默认 50s）就是 ERROR 1205，而不是无害的零行匹配。
`pkg/db/mysql.go` 对任何迁移错误都 `panic`，所以结果是 **B 启动 panic 并进入
CrashLoopBackOff**，不是幂等跳过。

**并发启动还有第二种失败形态，和 1205 是两回事。** 两个 pod 都把这条迁移算进
「待执行」计划，A 提交后 B 走到写 `gorp_migrations` 那一步撞主键重复，`sql-migrate`
返回错误，同样被 `pkg/db/mysql.go` 的 `panic` 接住。区别在于 B 这次**根本没跑**那条
UPDATE——数据是对的，pod 却起不来。它在重启后自愈（届时账本已有记录，计划为空），
所以症状是「第一次滚动时有 pod CrashLoop 一两次然后好了」，很容易被读成偶发。

这两种形态都不是本 PR 引入的，是本仓 **启动即迁移** 设计的固有属性——没有任何地方取
advisory lock，任何新迁移都同样暴露。`octo_project` 建于 2026-09-04，基数小，所以这次
的实际风险低；写在这里是因为运维看到 CrashLoop 时需要知道该不该回滚（不该）。

`kubectl rollout restart`、节点 drain、`maxSurge > 1` 都会并发起 pod。首次升级请
**串行放量**（先让一个 pod 完成迁移再放其余），或在该窗口把副本数临时降到 1。

对账扫描里的修复语句不受影响——它按 `project_id` 定位单行。

## 4.1 首次升级的执行步骤（按顺序，不要跳）

回填语句本身是幂等的，**但并发启动不是**（见上一节）。所以第一次带这个迁移上线时：

1. **把副本数降到 1**（或确认 `maxSurge=0`，即滚动更新一次只起一个 pod）。
   `kubectl rollout restart`、节点 drain、`maxSurge > 1` 都会并发起 pod。
2. 部署新镜像，**等这一个 pod 就绪**。大表上它的就绪会明显变慢，那就是回填在跑。
3. 确认迁移账本里已有 `20260908000002`：
   `SELECT id, applied_at FROM gorp_migrations WHERE id LIKE '%project_member_epoch_base_one%';`
   有记录才说明回填已提交，后续 pod 会跳过它。
4. **确认没有活跃项目还落在 0 上**：
   `SELECT COUNT(*) FROM octo_project WHERE status = 1 AND member_epoch = 0;`
   期望 0。不为 0 说明有实例还在按旧逻辑写入（见第 2 节）。
5. 恢复副本数 / 正常滚动。

这五步是**要执行并留痕的发布门禁**，不是一段建议性文字：第 1 步和第 3 步是上一节两种
失败形态唯一的防线，而它们都以 CrashLoop 的形式出现，事后很难和别的原因区分。

第 2 步之后再起并发 pod 就是安全的：谓词不再匹配任何行，语句是空操作。

## 5. 完整轴清单：哪些变化会移动 epoch，哪些不会

对端把 epoch 一致当作「缓存仍然有效」的判据。这里逐条写清楚哪些事件会让它变，因为
**漏掉任何一条，都等于对端拿着一个它自己检查不出过期的授权**。

| 变化 | epoch 会动吗 | 机制 |
|---|---|---|
| 项目成员增删 / 改角色 | ✅ 同事务内 +1 | 写路径直接 bump |
| 项目解散 | ✅ | 先 bump 再翻 status；随后它从 epochs 结果里掉出，读作 `0` |
| **Space 封禁 / 解封** | ✅ | 不写项目行，但 epochs 的谓词会把父 Space 不活跃的项目折成 `0`；解封后恢复原值 |
| **Space 解散** | ✅ | 同上。注意本仓**不会**级联解散其下项目，它们的 `status` 永远是 1——全靠这条谓词 |
| **Space 成员移除** | ✅ **同事务内 +1** | 见下 |
| **Space 成员重新加入**（四条路径全覆盖） | ✅ **同事务内 +1** | 与移除对称。移除的异步级联若还没跑到，此人的项目席位仍然存活；重新打开 Space 席位会让那个席位**重新可达**，而这中间没有任何项目侧写入，所以必须在重新加入的事务内 bump——否则对端缓存的那条**拒绝**会一直和 epoch 对得上，一个合法回归的成员被无上界地拒绝。四条路径见下 |
| **账号被全局封禁 / 注销** | ❌ **不会动**（已记录的偏离） | 见下「账号轴」 |
| **Bot 被删除** | ✅ **同事务内 +1** | 曾是本文档记录的偏离，现已闭合。见下「Bot 轴」 |

### Space 成员移除为什么必须在事务内 bump

移除该成员的项目席位是**异步**的：移除事务只写一条清理工单，真正关席位的作业可能在
退避里待上几分钟，而且**重试 20 次耗尽后进 abandoned 终态，不再被任何东西认领**。

如果 epoch 等到关席位时才动，那么在这段时间里：`_verify` 已经答 `member:false`
（它会合取 Space 成员资格），而 `epochs` 还答旧值——对端重读 epoch 拿到同一个数，
**过期检查通过，被撤销的授权继续有效**。正常路径上是几分钟，作业 abandoned 之后是永久。

所以移除事务内会执行一条语句，把该成员还持有席位的所有活跃项目的 `member_epoch` 一次性
+1。**这条语句失败会让整次成员移除回滚**——宁可让调用方重试，也不要提交一次没有失效
信号的移除。

### 重新加入有四条路径，按 SQL 枚举而不是按函数名

这一条本来只覆盖了两条，第九轮 review 在引擎上证伪了「已全覆盖」的声明。四条都会把一个
已存在的 `space_member` 行从 `status=0` 翻回 `1`，因此都会让移除窗口里**存活的项目席位重新
可达**：

| 路径 | 入口 |
|---|---|
| `reactivateMember` | 邀请 / 重新添加 |
| `atomicReactivateMemberIfNotFull` | 加入（带容量校验） |
| `approveJoinApplyAtomic` 的重新激活分支 | 申请审批（空间内 / 管理端 / H5 auth_code 三个入口都汇聚到它）|
| `upsertMembers` 的 `ON DUPLICATE` 分支 | 管理端强制添加 `POST /spaces/:space_id/members` |

**教训写在这里，因为它会重犯**：后两条的函数签名里没有任何「reactivate」字样，
`approveJoinApplyAtomic` 甚至是**设计好的重新加入漏斗**（`resetApprovedApplyForRejoin` 存在的
目的就是让被移除的人重新走审批回来）。按名字枚举会漏掉一半；要按 SQL 枚举 ——
`ON DUPLICATE KEY UPDATE status=1` 撞上唯一索引就是一次重新激活，不是插入。

**另外：判定「这次是不是重新激活」不能用 `ON DUPLICATE` 的 affected-rows。** 实测
（MySQL 8.0.33）：全新插入=1、重新激活=2、而**已活跃成员跨秒重复 upsert 也是 2**（因为
`updated_at=NOW()` 让它算「有变化」）。按 `affected==2` 分流会让每次重复添加都 bump 一次
epoch，破坏「空写不动 epoch」这条对端缓存所依赖的规则。所以走 upsert 前的锁定读。

### 标识符也必须来自数据库，不只是判定

第十二轮 review（两位 reviewer 独立汇聚）发现前面那条「判定来自写入」只走完一半：布尔值
搬进了数据库，**传给失效步骤的标识符还是调用方发来的那串字节**，而它接着要去匹配一张
collation 更严的表。

- `space_member` 生产上是 `utf8mb4_0900_ai_ci`（dump 导入的产物）
- `octo_project_member` 被每条迁移显式钉成 `utf8mb4_general_ci`
- 两者的等价类**不同**，且方向危险：`0900_ai_ci` 走 UCA 9.0.0 主权重，会把**兼容性分解**
  折到基字符；`general_ci` 是逐字符的旧表，不折。

实测（MySQL 8.0.33，两个生产 collation，库里存 `alice`）：

| 请求拼写 | `0900_ai_ci` | `general_ci` | |
|---|---|---|---|
| U+FF41 全角 a | 1 | **0** | 分歧 |
| U+212A KELVIN SIGN | 1 | **0** | 分歧 |
| U+2126 OHM SIGN | 1 | **0** | 分歧 |
| U+00AA 阴性序数符 | 1 | **0** | 分歧 |
| U+017F 长 s | 1 | 1 | 不分歧 |
| U+00E9 é | 1 | 1 | 不分歧 |
| ASCII 大小写 | 1 | 1 | 不分歧 |

**分歧类不是「宽度」，是「有兼容性分解且基字符是拉丁字母」。** 这一点值得单独记：四个人
（三位 reviewer 加作者）各自挑了一个字符去论证，其中三次挑错 —— 重音被两份评审当成分歧
实例（不是），KELVIN 被一份测成不分歧（是分歧，测法有误）。**这个类不能靠举例来定义**，
这正是把标识符交给数据库、而不是维护一张字符清单的理由。

后果与「漏 bump」完全同类，且移除方向更糟：席位真的关了（松 collation 匹配得上），
`octo_project_member` 枚举到 0 行 → epoch 不动 → `_verify` 答 `member:false` 而 `epochs`
仍答授权被缓存时的旧值，对端的过期检查与自己一致，**被撤销的授权无限期存活**。异步级联
也不是兜底：工单里存的是同一串漂移拼写，级联先用松 collation 匹配上 Space 成员、再枚举到
0 个项目席位，然后**成功**收工 —— 项目席位永久孤儿。

**一行席位有两个身份列，两个都要。** 第十三轮 review（两位再次独立汇聚）发现上一轮的
`SeatRef` 只规范化了 `uid`，`space_id` 仍是调用方的字节 —— 而 epoch 步骤匹配的是**这一对**
（`WHERE space_id = ? AND uid = ?`）。规范化一列而放过另一列，失效信号一样是死的。

`space_id` 不比 `uid` 安全：它虽然是服务端生成的，但**每次移除/踢人/退出/重新邀请请求都由
调用方带上来**，而 ID 里可能出现的每个 ASCII 字符都有对应的全角形（实测：数字、十六进制
字母、下划线全部 `0900_ai_ci` 折叠而 `general_ci` 不折）。漂移的 `space_id` 能通过 Space
中间件（它 JOIN 的 `space_member`/`space` 都是松 collation）、翻转席位、然后走到步骤这里。

**门矩阵此前对这条轴结构性失明** —— 它只漂移 uid，`space_id` 在每个用例里都是规范的。现在
两列一起漂移、两列一起断言。

**落地方式是类型而不是纪律**（`modules/space/seatref.go`）：

- `SeatRef` 字段不可导出，没有从 `string` 的转换 —— 想构造只能经 `ResolveSeatTx`，
  它在写入命中那一行之后、锁还握着的时候把 `space_id` 和 `uid` **两列**一起读回来。
- 事务步骤注册表、outbox 入队都只收 `SeatRef`。**把调用方的字符串传进去编译不过。**
- 准入侧同样，而且也是两列：`octo_project_member.uid` 取自 `space_member` 返回的拼写
  （`pkg/project.FoldedLookup`）；`octo_project.space_id` 取自 `lockSpaceRowTx` 锁住的
  `space` 行、`octo_project_member.space_id` 取自锁住的项目行、`octo_project.creator`
  取自 `lockSpaceSeatRowTx` 锁住的席位行。这三处此前都是 `SELECT 1`／直接用请求参数，
  等于把权威表已经握在手里的字节丢掉。所以两张表存的字节一致，而不是靠某个 collation
  去弥合。

准入侧那一条不是可选的。两位 reviewer 都写了「由不变量 I1 保证规范拼写天然匹配」——
**这个论证不成立**：I1 说的是成员关系，不是字节相等。真正挡住漂移拼写进入
`octo_project_member` 的是准入门的 `FoldedHas` 折叠，而 `FoldID` 是刻意 ASCII-only 的，
所以所有真正分歧的拼写都在那里 fail-closed 被拒。那是一条跨两个包、无人维系的耦合，而且
在一个**看起来是改进**的变更下会静默失效：把 `FoldID` 改成宽度感知（更贴近数据库的等价类）
会让漂移拼写开始进入项目席位，移除侧的规范化随即不再覆盖它们。写入规范拼写是**消除**这个
依赖，而不是把它记录下来。

### 账号轴：全局封禁 / 注销 —— 只挡新答案，不动 epoch（已记录的偏离）

超管封禁只写 `user` 行（撤销 session、踢设备、封 IM 频道），账号注销也**不会**级联删除
任何成员行。也就是说被封禁 / 已注销的 uid，`space_member` 与 `octo_project_member`
两行都还是 `status = 1`。

**新鲜答案已经挡住了。** `_verify` 现在会合取账号存活
（`user.status = 1 AND user.is_destroy <> 2`，`pkg/user.ActiveAccounts`），准入侧也
一并挡了（被封禁账号不能被加进项目、也不能建项目）。冷静期（`is_destroy = 1`）仍算活跃，
因为那种账号还能正常收发消息。

**但封禁**不会**移动 epoch**，这是本次交付明确接受的偏离：封禁路径在 `modules/user`，
让它去 bump 项目 epoch 需要引入跨模块依赖，不在本片范围内。后果是**封禁之前已经被对端
缓存的那条肯定授权，会一直和 epoch 对得上**。

对端需要知道的：**对缓存的判定加一个独立于 epoch 的上限 TTL**。epoch 一致对本轴不是
充分条件。封禁本身会撤销 session 与设备，所以持 token 的路径当场就断了；真正暴露的只有
「对端拿着自己缓存的旧判定、不再回来问」这一种。

### Bot 轴：Bot 删除 —— 已闭合（此前是本文档记录的偏离）

**曾经的缺陷**：`modules/botfather` 直接写一条跨 Space 的
`UPDATE space_member SET status=0 WHERE uid=?` 来删除 Bot —— 一条语句改掉该 Bot 在**所有**
Space 的席位，不在事务里、不排清理工单、不动 epoch。而项目准入不排除 Bot（Bot 可以持有
`octo_project_member` 席位，本仓自己就会把创建者的分身放进项目），于是：`_verify` 会答
member:false（Space 合取看得见这次关闭），而 `epochs` 一直答删除前的值 —— 对端缓存的肯定
授权永不失效，且因为清理工单也没排，**没有任何东西会去关掉那个项目席位**。

**现在的机制**（两步，分别由两个 PR 落地）：

1. PR #855 把三个删除入口（botfather 命令、botfather REST、管理端 REST）统一改走
   `modules/space.CloseAllSpaceSeats`：按 Space 逐个、在事务内关席位并写清理工单，
   关席位失败会让整次删除中止，而不是留下没人能扫到的残留。
2. 本片补上它缺的那一半 —— 那条路径写了 outbox 但**没跑事务内步骤**，所以 epoch 仍然不动。
   现在 `closeOneSeatAndEnqueueTx` 在同一事务里经 `closeSeatTx` 跑 `runSeatTransitionTxSteps`，与另外两条关席位
   路径共用同一个注册表、同一条 bump 语句。

**为什么必须是同一条语句、同一个注册表**：关席位的路径有三条（单成员移除、管理端批量移除、
跨 Space 关闭）。任何一条漏掉这一步，**那一类 uid 的 epoch 一致性就不再是充分条件**，而对端
无法按 uid 类型区分对待。所以这里的「一致」不是整洁，是正确性。

**回归网**：`TestBotSeatCloseMovesTheEpoch`（关席位后 epoch 必须动、无关项目不得被搅动），
以及 `space_member` 写入方源码 sweep —— 它枚举每一个写入方并要求登记理由，新增写入方、
计数变化、以及模式匹配不到任何东西（变异验证过）三种情况都会失败。

### 运维注意

- 一次移除会让该成员所在的**每个**项目的 epoch +1，对端因此对这些项目各多做一次重新
  校验。这是必要代价。
- 兜底告警 `scanAbandonedCleanupLeak`（「Space 成员移除工单已 abandoned，项目席位仍活跃」）
  在 `OCTO_PROJECT_RECONCILE_ENABLED` 门内，而该开关**默认关闭**。**对人类成员的移除**
  而言，席位泄漏本身不再影响授权正确性（epoch 已经在移除时动过了），但它仍是需要人工介入
  的状态——**建议开启**。Bot 删除现在也走同一套工单与
  失效信号（见上「Bot 轴」），所以这个告警覆盖它，这句结论对它同样成立。

## 6. 监控

指标名按**可抓取的序列名**写，不是 Go 标识符——本文档此前写的 `epochAnomalies` 是后者，
按它写的告警规则不会命中任何东西。

- `project_member_epoch_anomalies_total`（**Counter**）：负值、同副本回退，以及
  **活跃项目落在 0 上并被修复**三类合一。上线完成后增量应当归零；持续增长意味着
  仍有按旧逻辑写入的实例。告警按 `increase(...[1h]) > 0` 写。
- `octo_internal_membership_configured`（**Gauge**）：1 = `OCTO_MEMBERSHIP_INTERNAL_TOKEN`
  在启动时解析成功、内部端点可以鉴权；0 = 未设置 / 太短 / 与兄弟能力的 token 撞车。
  端点对「未设置」和「token 错」返回同一个 401，**这个 gauge 是运维唯一能区分两者的地方**。
  在对端交付缓存时间上界之前，这个值应当保持 0——见第 7 节的启用门禁。
- 修复日志：`活跃项目的 member_epoch 落在契约保留的 0 上，已提升为 1`，带 `projectId`。
  单轮条数受 `reconcileLogCap` 限制。

## 7. 启用门禁：设 token 一个变量**打不开**这个能力

`OCTO_MEMBERSHIP_INTERNAL_TOKEN` 单独设置**不会**启用这两个内部端点。还必须同时设置：

```
OCTO_MEMBERSHIP_INTERNAL_PEER_MAX_CACHE_AGE_SECONDS=<1..300>
```

含义是：**对端对它缓存的判定所施加的时间上界（秒）**。建议起点 30。

任一情况下能力保持关闭，并打一条 ERROR 说明原因：变量缺失、非整数、`<1`、`>300`。
`octo_internal_membership_configured` 停在 0，`octo_internal_membership_peer_max_cache_age_seconds`
停在 0。

### 为什么把发布条件做成一个变量

第 5 节「账号轴」那一行是结构性的，不是实现缺陷：epoch 按 **project** 键控，而全局封禁
和注销是 **per-user** 的事实。封禁不写 `space_member`、不写 `octo_project_member`，因此
不存在一行可以 bump——被缓存的**授权**会一直和 epoch 对得上，被缓存的**拒绝**在解封后
也一样。这一轴唯一的上界在对端，靠时间。

在此之前，这个前提写在 PR 描述和本文档里，靠人记得。本分支花了十几轮把「必须记得做的
事」从代码里消掉（`SeatRef` 让传错标识符编译不过，席位漏斗让「漏掉某一步」的决策点从
七个降到一个），却没有把同一条纪律用在自己的发布条件上。现在用上了：**要开这个能力，
就必须把那个数写出来。**

写「数值」而不是一个 yes/no 确认位，是因为数值才是契约本身。提案 §3.1 的
`max_age_seconds` 上线后，应答里那个字段的取值就来自这里，不会有第二个来源漂移。

### 开 token 之前还必须关掉的一件事（不在本分支范围内）

`modules/botfather/mint_obo.go` 把 `req.SpaceID`（HTTP body 直取，
`modules/bot_provision/bot_api.go`）直接 INSERT 进 `space_member`，全程不读 `space` 行。
它前面的 `assertSpaceMember` JOIN 的是 `space_member`/`space`/`user`，生产上都是
`utf8mb4_0900_ai_ci`，所以一个全角漂移的 space_id 能通过这道门、把带漂移字节的席位写进去。
之后关席位时 `ResolveSeatTx` 忠实读回漂移字节，epoch 枚举在 `general_ci` 下查不到任何
项目席位——这就是第 12/13 轮那条陈旧授权链路，端到端可达。

它没有在本分支修，因为修的地方在 `modules/bot_provision`（`MintBotOBO` 得去读 `space` 行，
它本来也该做存活校验），而本分支不改那个模块。两位 reviewer 都判为「立 issue + 作为开 token
的前置条件」，理由是：**面向对端的那一半被上面的两个 env 门禁挡死了**，而**现在就活着的那一半**
（一条级联永远够不到的孤儿 `octo_project_member` 行）在 main 上本来就存在，跟本分支无关。

写在这里是因为它属于「开 token 之前」而不是「合这个 PR 之前」。同类但可达性低得多的
`atomicJoinInitialSpace` 已在本分支修掉（配置来源、权威行在手），见
`modules/space/disband_space_id_spelling_test.go`。

### 这个门禁不保证什么

它不能证明对端**遵守**了那个上界——服务端在启动时无从验证。提案 §5 描述的是可实测的
版本（按对端标识统计 `_verify` 复查间隔的 p99，稳定 ≤ 上界才放行）。当前这一步做到的是：
把一个**没写出来的假设**变成一个**写出来的假设**，并且可观测。上线签字仍然需要人确认
对端确实实现了 §4 的三条。
