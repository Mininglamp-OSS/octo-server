## 1. 背景与问题

### 1.1 业务诉求

OCTO 是可自部署的企业协作 IM。当两家企业各自部署了自己的 OCTO 实例后，跨企业协作目前**无解**：

> 甲方公司和乙方公司要就一个项目长期协作。双方各有自己的 OCTO 实例，各自管着自己的员工、数据和合规边界。他们希望有一个**共享的项目群**，双方成员都能在里面发消息、传文件、@对方。

现状下他们只有三个坏选项：

| 现有做法 | 问题 |
|---|---|
| 一方给对方开账号 | 对方成了你的"员工"，进你的通讯录，看得见不该看的；对方也不愿意员工身份挂在别人系统里 |
| 双方都用某个公有云 IM | 数据出境 / 离开自建边界，自部署的意义没了 |
| 微信 / 邮件外挂 | 协作上下文碎裂，无法审计，附件与消息脱管 |

这就是业界常说的 **Slack Connect / 企业微信外部群** 那一类能力，但**前提是双方各自自部署**。

### 1.2 为什么现在提

已有的「外部群」功能（见 `external-group-design.md`）解决的是**同一个实例内、跨 Space** 的外部协作。它的前提是：

```
同一个数据库  +  同一个 WuKongIM  +  同一份 user 表
```

跨**实例**是另一个问题 —— 数据库不通、用户表不通、消息总线不通。代码里对此**零支持**（全仓搜 `federat` 无任何命中）。

## 2. 目标与非目标

### 2.1 目标

- 两家独立部署的实例之间建立**互信认证**
- 双方用户在一个**共享外部群**里正常收发消息、传附件、@提及
- 联邦成员在群里**显著可识别**（不能伪装成本地成员）
- **不改动 WuKongIM**（消息总线保持为不感知联邦的哑管道）
- 复用现有「外部群」的产品语义，不另起一套平行概念

### 2.2 非目标（明确划出）

| 非目标 | 原因 |
|---|---|
| 双向复制（各存一份） | 见 §5.2；成本远超收益 |
| 开放联邦 / 动态发现任意实例 | 起步只做**带合同的点对点配对**，不做公开联邦网络 |
| 联邦群的端到端加密 | 服务端中继下物理上不成立，见 §9.3 |
| 修改 WuKongIM 源码 | 核心设计约束 |
| 把联邦身份编进 uid 字符串 | 见 §4.1，此路已封死 |

## 3. 现状：我们已经有什么

理解方案前先看清底牌 —— **有相当一部分是白送的，缺的是特定的一块**。

### 3.1 ✅ 外部成员的产品语义（约 70% 已存在）

现有「外部群」已实现并上线：

- `is_external=1` 成员标记 + 外部角标渲染
- `source_space_id` 来源标识
- `allow_external` 群级安全阀（可禁止外部成员加入）
- 最后一个外部成员退出后自动恢复为普通群
- 会话列表过滤放行（`space_filter.go`）
- 搜索过滤放行（`shouldIncludeGroupForSpace`）

**联邦要做的不是重造这些，而是替换它们的身份来源。**

### 3.2 ✅ WuKongIM 是一条可以不动的哑管道

这是整个方案可行的关键，且**有实测证据**：

```
                    ┌─────────────────────────────────┐
                    │          WuKongIM               │
                    │  只认 uid 字符串和 channel_id    │
                    │  不理解 Space / 组织 / 联邦       │
                    └─────────────────────────────────┘
                          ▲                    │
      octo 告诉它「谁在这个频道」  │                    │  它回问「这个频道有谁？」
                          │                    ▼
                    ┌─────────────────────────────────┐
                    │          octo-server            │
                    │      业务语义的唯一权威方          │
                    └─────────────────────────────────┘
```

- IM 通过 `POST /v1/datasource` + `cmd=getSubscribers` **反向问 octo 要成员名单**，并无条件采信
- `IMAddSubscriber` 只接受 **uid 字符串**，无注册握手
- IM token **仅在真实登录时铸发** → 一个从不连接的订阅者在 IM 侧不需要身份

→ 所以可以把远端用户做成「从不登录的订阅者」塞进 IM，IM 不会追问它是谁。

### 3.3 ✅ 可直接复用的两个现成件

| 现成件 | 复用方式 |
|---|---|
| `user_oidc_identity` 表结构 | 形状恰好是 `(issuer, subject) → 本地 uid` 带唯一键。把 `issuer` 换成对端实例，即联邦身份映射表 |
| webhook 的 HMAC-SHA256 签名（fail-closed） | 作为实例间互信的起步原语 |

### 3.4 ❌ 完全缺失的：身份底座与信任层

- uid 是**每实例本地生成**的 32 位 hex，无命名空间限定
- 认证 token 是 Redis 里的**不透明随机串**，跨实例无法验证
- JWT / JWKS 基建**已被刻意移除**
- 无 mTLS，无实例间信任概念

**一句话概括现状**：外部群的"衣服"已经有了，缺的是能穿这身衣服的"人"，以及两家握手的"介绍信"。

## 4. 核心难点

### 4.1 🔴 联邦身份不能编进 uid（此路已封死）

直觉方案是 `alice@company-b.com` 这种域名限定 uid。**两条路都堵死**：

| 障碍 | 细节 |
|---|---|
| **`@` 是保留字符** | `IsFakeChannel(id)` 的判定就是 `strings.Contains(id, "@")`；单聊频道 ID 用 `from@to` 拼接。带 `@` 的 uid 会被**全系统误解析成一个单聊会话**。非测试调用点 9 处 |
| **列宽写死 40** | `uid VARCHAR(40)`，现用 32 hex，只剩 8 字符余量。跨约 40 个 migration 一致且均带索引。⚠️ 另一模块曾尝试放宽到 64 并**已回滚**（原因待查） |

**→ 结论：联邦来源必须记在旁路表，绝不进 uid 字符串。**

### 4.2 🔴 非本地成员的失败模式是"静默消失"而非"报错"

`QueryByUIDs` 之后的循环遍历的是**数据库返回结果**而非请求列表 → 未知 uid 被**无声丢弃，不报错**。

更糟的是外部标记：远端来源无法解析出名称时，外部角标会被**整个丢掉** → 联邦成员渲染成**无标记的普通成员**。这是安全上最坏的结果（伪装成本地人）。

**→ 所以远端用户必须在本地有真实存在的行，而非"虚拟成员"。**

### 4.3 🔴 认证 ≠ 授权

HMAC 验签只证明「请求来自持有共享密钥的一方」。它**不证明**：

- 这个 `remote_uid` 当前确实属于该对端实例且有效
- 该用户仍是目标群的成员
- 该对端实例被授权向**这个**频道写入

漏掉任何一条，就退化成「**任意可信 peer 的任意用户可写任意群**」。

## 5. 方案选型

### 5.1 两条候选路线

```
方案 A · 单边托管                      方案 B · 双向复制
（推荐）                               （不采用）

  ┌────────┐      ┌────────┐          ┌────────┐      ┌────────┐
  │ 实例 A │      │ 实例 B │          │ 实例 A │◄────►│ 实例 B │
  │        │      │        │          │        │      │        │
  │ ┌────┐ │      │        │          │ ┌────┐ │      │ ┌────┐ │
  │ │群  │ │◄─────┤ 中继   │          │ │群镜│ │◄────►│ │群镜│ │
  │ │(唯一)│      │        │          │ │像  │ │      │ │像  │ │
  │ └────┘ │      │        │          │ └────┘ │      │ └────┘ │
  └────────┘      └────────┘          └────────┘      └────────┘

  群只存在一份，寄居在 A            两边各有一份镜像，需状态收敛
  B 用户投影为 A 上的影子            双方都是权威方
```

### 5.2 为什么不选双向复制

| 阻碍 | 说明 |
|---|---|
| Token 无法跨实例验证 | 认证 token 是 Redis 不透明串，「校验」本质是一次 Redis GET。实例 B 无从验证 A 的 token |
| JWT 基建已被移除 | 联邦最需要的可验证签名原语恰好被删掉了 |
| 还得自解一堆分布式难题 | 消息去重、乱序、编辑/撤回同步、附件跨域、成员状态收敛 |

**净效果**：选 B 等于「先自建一整套联邦协议，才能写第一行业务代码」—— 基本是重写一遍 Matrix 的联邦状态解析。

**→ 选 A 做 MVP，但把联邦网关抽成独立模块 `modules/federation`，不把「单边」假设焊进业务代码**，为未来可能的 B 留扩展位。

```
               🔴 关键：B 的用户从不接触 A 的 IM，也不持有 A 的凭证
                       跨实例只在两个 federation 网关之间发生
```

### 6.2 为什么中继在服务端，而不给对方发凭证

另一条路是「给 B 的用户铸 A 的 IM token，让他们直连 A 的 IM」。**不采用**：

那等于**为不受自己管理的人铸发凭证**，并把消息总线暴露给不受信任的客户端。攻击面显著更大，且凭证吊销、设备管理、滥用处置全都失控。

服务端中继下，A 只需信任**一个**对端（网关），而不是对端的**每一个用户**。

### 6.3 影子身份：一个远端用户在 Host 上长什么样

```
       企业 B 侧                      映射表                      企业 A 侧
  ┌──────────────────┐                                    ┌───────────────────┐
  │ 真实用户          │      ┌──────────────────────┐      │ 影子账号（本地行） │
  │                  │      │ peer_instance_id     │      │                   │
  │ uid: 7f3a...     │─────►│ remote_uid           │─────►│ uid: b9f2...      │
  │ 昵称: 张三        │      │ local_shadow_uid     │      │ （本地 32 位 hex） │
  │ 部门/手机/邮箱    │      │ status / 租约         │      │ is_external=1     │
  │  ↑ 不投影         │      │ 昵称 / 头像（投影）    │      │ 联邦来源标记       │
  └──────────────────┘      └──────────────────────┘      │ 🔴 不可认证        │
                                                          └───────────────────┘
```

**三条硬约束：**

1. 影子 uid 是**正常生成的本地 32 位 hex**，不含任何域名或命名空间（§4.1）
2. 影子**必须同时落 `user` 表和 `group_member` 表** —— 只塞进 IM 订阅表会出三个 bug（§7.1）
3. 影子是**不可认证的**（unauthenticatable）：永不能登录、铸 token、绑定凭证、被全局搜索、加好友

> **为什么第 3 条要单列为一等约束**：影子在数据库里是一行**普通的 user 记录**，所以登录、token 铸发、密码/OIDC 绑定、设备注册、DM 发起、@提及、审计、管理后台、导入导出、GDPR 删除、权限缓存 —— **每一条路径都可能把它当真人对待**。必须逐路径审计并显式拒绝或降级。

## 7. 关键机制

### 7.1 🔴 影子必须"双侧落地"（实测得出的结论）

Phase 0 实测发现：只把影子 uid 加进 **IM 的订阅表**，IM 侧一切正常（收发、广播、fan-out 全通），但 **octo 侧对它一无所知** —— 由此产生三个 bug，且**根因同一、解法同一**：

| 现象 | 根因 | 后果 |
|---|---|---|
| 发送者**无名无头像** | octo 查不到该 uid 的展示信息（接口 400 / 头像 404 / 日志「用户不存在」） | 联邦用户在群里是个**幽灵** |
| 🔴 影子可能被**静默抹除** | 若启用 IM 的 datasource 回调，IM 会回问 octo 要权威名单 —— 而 `group_member` 里没有影子 | 下次订阅重载，影子**消失** |
| 每条群消息刷一条 error 日志 | 离线推送路径把影子当真实收件人查，查不到 | 按群成员数放大的日志噪音 |

**统一解法：影子同时写入 `user` + `group_member`（带 `is_external` 标记），而非仅存在于 IM 订阅表。**

> ⚠️ 第二条尤其危险：本地部署恰好**没开** datasource，所以"看起来没事"。换个开了的环境就炸。因此**不得**依赖「永久禁用 datasource」这种环境约定，必须从数据模型上解决。
>
> ✅ 附带利好：现有代码里所有 `IMAddSubscriber` 调用**都是增量添加**（无一处传 `Reset`），所以正常的建群 / 拉人 / 踢人流程不会误伤影子订阅。

### 7.2 入站消息的三段授权

每一条从对端进来的消息，**三关都过才收，缺一即拒**：

```
  对端消息到达
       │
       ▼
  ┌─────────────────────┐
  │ ① 对端认证           │  HMAC 验签 + 时间窗 + nonce 防重放
  │   「你是谁」          │  ✗ → 拒绝
  └──────────┬──────────┘
             ▼
  ┌─────────────────────┐
  │ ② 身份绑定           │  该 remote_uid 在映射表中存在、
  │   「这人还有效吗」    │  状态有效、租约未过期
  └──────────┬──────────┘  ✗ → 拒绝
             ▼
  ┌─────────────────────┐
  │ ③ 频道授权           │  目标群允许外部成员、该群已与该对端
  │   「你能写这个群吗」  │  建立联邦关系、该影子是该群成员
  └──────────┬──────────┘  ✗ → 拒绝
             ▼
        接受，入库中继
```

🔴 联邦入站**必须显式携带并强校验频道归属**。现有 Space 中间件在「请求未带 space_id」时会**整段跳过校验** —— 联邦路径不得依赖这个口子。

另外，频道引用**不能是可猜测的自由字符串**（否则等于让对端自行选择要写哪个群）。用**不可猜测的联邦频道 token**，由 Host 侧做权威解析。

### 7.3 可靠投递：收发件箱

「写入 IM」和「记录幂等标记」不在同一个事务里 → 崩溃窗口会造成**消息重复或永久丢失**。

```
  入站：  对端 ──► 收件箱（事务内落库，(对端, 幂等键) 唯一）
                      │
                      └──► worker 幂等地写入 IM

  出站：  本地消息 ──► 发件箱（事务内落库）
                      │
                      └──► worker 带 ACK / 重试 / 死信投递对端
```

需定义：保留期、最大重试次数、死信队列、崩溃恢复（重启后扫描未 ACK 项）。

⚠️ 对端传来的时间戳**不可作为排序权威**（时钟偏移），仅用于展示；排序以本地接收序为准。

### 7.4 出站捕获挂在哪（已实测定位）

WuKongIM 经 **gRPC** 把消息事件推给 octo-server。中继逻辑应挂 **`msg.notify`** 事件 —— 它对频道内**每条**消息触发一次，与收件人在线/离线无关。

🔴 **不要挂 `msg.offline`** —— 那条只在存在离线收件人时才来，会漏消息。

### 7.5 附件跨域

两个实例的对象存储各自本地，跨实例取不到文件。

**采用异步拉取**：中继消息只带**附件元数据 + 对端签名下载 token**；Host 落消息后由**异步 Worker 回源拉取**并转存本地存储，改写为本地 URL。

> 为什么不同步推送字节流：几十到几百 MB 的文件经 HTTP 网关同步推送会造成连接堆积、内存膨胀、超时，**反而把整条中继搞挂**。异步拉取同样保留「内容落 Host」这一数据主权属性。

需定义：大小/类型前置校验、内容哈希校验、对象写入与消息引用的原子提交、重复上传幂等、吊销后历史附件的访问策略。

### 7.6 生命周期：事件驱动 + 租约兜底

**问题**：B 公司员工离职后，A 公司群里那个影子怎么办？

```
  主路径（事件驱动）        对端主动推送生命周期事件
                          （停用 / 吊销 / 入群 / 退群 / 改昵称头像）
                                     │
                                     ▼
                          Host 即时处置，无需轮询

  兜底（租约）              长时间收不到任何事件 → 租约过期
                          → 转为「暂停」（禁止发言 + 标记不活跃）

  重连对账                  网关断线重连后做一次全量同步
```

> 为什么不用周期性轮询：数百成员规模下是 O(N) 的无效轮询，且存在生命周期竞态可被绕过。

🔴 **吊销必须是线性化的**：需**原子失效**在途请求 + 成员缓存 + 权限缓存，否则已被吊销的用户可借在途请求或陈旧缓存继续写入。

## 8. 端到端场景

### 场景 1 · 建立联邦关系（一次性，人工介入）

```
  管理员 A                    管理员 B
     │                           │
     │◄──── 带外交换共享密钥 ────►│   （不经系统，不入日志，不进文档）
     │                           │
     ▼                           ▼
  登记对端实例                 登记对端实例
  （地址 + 密钥）              （地址 + 密钥）
     │
     ▼
  为具体群开启联邦（显式白名单，默认拒绝）
```

**要点**：授权粒度是**到具体群**的白名单，不是「对端可写任意群」。

### 场景 2 · B 的用户加入共享群

```
  1. A 侧管理员邀请 B 侧成员（或 B 侧成员经邀请链接加入）
  2. A 的网关向 B 校验该用户身份有效
  3. A 侧创建影子：
       ├── 映射表登记 (对端, remote_uid) → 本地影子 uid
       ├── user 表落行（不可认证，投影昵称 + 头像）
       ├── group_member 落行（is_external=1 + 联邦来源标记）
       └── IMAddSubscriber 把影子加入 IM 频道
  4. 群内所有人看到「XX 以外部成员身份加入」+ 外部角标
```

⚠️ **并发陷阱**：多条消息可能瞬间并发触发同一用户的影子创建，撞唯一键导致 500 + 丢消息。**必须用数据库级 upsert 或按键加锁**，禁止「先查询再插入」的裸竞态。

### 场景 3 · B 的用户发一条消息（入站）

```
 B 用户发消息
      │
      ▼
 B 的 octo-server 识别该频道为联邦频道
      │
      ▼
 B 的网关 ──HTTPS + HMAC 签名──► A 的网关
      │
      ▼
 A 的网关：三段授权（§7.2）
      │  ✗ 任一不过 → 拒绝
      ▼
 解析 remote_uid → 本地影子 uid
      │
      ▼
 落收件箱（幂等）
      │
      ▼
 以影子 uid 身份写入 A 的 IM 频道
      │
      ▼
 A 的 IM 广播给群内所有订阅者
      │
      ▼
 A 侧用户看到消息，发送者显示为「张三 · 外部 · 来自 B 公司」
```

✅ 这条链路的关键前提（以影子 uid 服务端发送、IM 接受并广播）**已实测通过**。

### 场景 4 · A 的用户回复（出站）

```
 A 用户在群里发消息
      │
      ▼
 A 的 IM ──gRPC msg.notify──► A 的 octo-server
      │
      ▼
 网关识别为联邦频道 → 落发件箱
      │
      ▼
 worker ──HTTPS + HMAC──► B 的网关（带 ACK / 重试 / 死信）
      │
      ▼
 B 侧同样做三段授权 → 写入 B 的 IM
      │
      ▼
 B 侧用户在自己的客户端看到 A 的消息
```

### 场景 5 · B 的员工离职

```
 B 侧停用该账号
      │
      ▼
 B 推送「用户已吊销」生命周期事件
      │
      ▼
 A 侧：影子状态置为吊销
      ├── 从群成员移除
      ├── 后续发言一律拒绝
      ├── 🔴 原子失效在途请求 + 成员缓存 + 权限缓存
      └── 历史消息保留（作者标注为已失效的外部成员）
```

若 B 侧未推送事件（网关故障 / 实现缺失），**租约过期**会兜底把影子转为暂停状态。

### 场景 6 · 联邦关系解除

```
 任一方删除对端登记
      │
      ▼
 立即 fail-closed：
      ├── 后续跨实例请求一律拒绝
      ├── 失效积压的重试队列、连接池、权限缓存
      └── 群退回普通群（最后一个外部成员移除后自动恢复）
      │
      ▼
 ❓ Host 上已存的对端数据是否必须清除？ ──► 见 §12.1（待确认）
```

## 9. 安全模型

### 9.1 双重总开关

联邦生效需**两个前置同时成立**，缺一即拒，默认关闭：

1. 群级 `allow_external=1`（复用现有安全阀）
2. 该对端实例登记状态为有效

### 9.2 联邦成员的可见性边界

| 信息面 | 联邦影子能看到 | 说明 |
|---|---|---|
| 该联邦群的消息与附件 | ✅ | 协作所需 |
| 群成员列表（带外部角标） | ✅ | 仅该群成员 |
| Host 的其他 Space / 其他群 | ❌ | 隔离 |
| Host 的用户目录 / 全局搜索 | ❌ | 仅群内可见 |
| Host 的好友关系图 / 组织架构 | ❌ | 隔离 |

**反向约束（§6.3 第 3 条）**：影子不可登录、不可被全局搜索、不可加好友、不可发起或接收单聊。

### 9.3 端到端加密：明确的已知限制

**服务端中继下 E2E 物理上不成立**：Host 必须见明文才能以影子身份落库和投递；影子在 Host 没有真实设备密钥；附件在 Host 以明文转存。

**处置：双向 fail-closed 硬闸**

- 已开 E2E 的群 → 拒绝开启联邦
- 已开联邦的群 → 🔴 **同样拒绝开启 E2E**（只拦一个方向会造成损坏的混合态）

并向用户**明示**「跨企业协作群，非端到端加密」。

### 9.4 其他必要防护

| 面 | 措施 |
|---|---|
| 重放攻击 | 签名覆盖规范化输入 + 时间窗 + nonce 去重。需区分「网络重试」（幂等吸收）与「重放攻击」（拒绝） |
| 密钥轮换 | 信封带密钥 ID，双密钥窗口内新旧都验，窗口结束废弃旧密钥 |
| 密钥托管 | 加密存储 + 版本管理；**带外人工交换，永不回显 / 不入日志 / 不进文档** |
| 🔴 SSRF / 路由劫持 | 管理员配置的对端地址若不约束，网关会向内网或错误主机推数据。**仅允许 https；解析 IP 后拒绝私网 / 环回 / 元数据段；禁止跟随重定向**。HMAC 不防错目的地 |
| DoS | per-peer 限流（防单个被攻陷的对端洪泛） |
| 合规审计 | 跨实例流量审计日志（记录谁经边界发了什么） |

## 12. 待确认事项

### 12.1 🔴 数据主权 —— 唯一无推荐值的决策（硬闸）

单边托管下，对端的协作数据（消息 / 附件 / 成员昵称头像）**物理存放在 Host 的服务器上**。

需明确：

- 两家法务是否接受这一存放方式？
- 谁是数据控制者（controller）、谁是处理者（processor）？
- 是否构成跨境数据传输？
- **联邦关系解除后，Host 是否必须清除对端数据（删除权）？**

**这是法律与合规判断，非工程判断。设计侧不提供推荐值。**

🔴 **本条未获明确确认前，不得推进到 Phase 1 之后。**

### 12.2 其余决策点（均已给出推荐值）

以下七项均已在 `federation-design.md` §16 给出**推荐值与理由**，评审时逐条确认或否决：

| 决策点 | 推荐值 |
|---|---|
| 互信原语 | HMAC 共享密钥起步，留 mTLS / JWT 迁移接缝 |
| 端到端加密 | 接受联邦群非 E2E，施加双向硬闸 |
| 消息流形态 | 服务端中继（而非给对端用户铸发本机凭证） |
| 附件传输 | 异步拉取并转存 Host |
| 影子信息投影范围 | 仅昵称 + 头像；不可被单聊 |
| `short_no` 分配 | 不为影子分配 |
| 托管方归属与授权粒度 | 发起方托管；per-peer 白名单到具体群，默认拒绝 |

## 附：术语表

| 术语 | 含义 |
|---|---|
| **Host（托管方）** | 共享外部群实际寄居的那个实例 |
| **Peer（对端）** | 与 Host 建立联邦关系的另一家实例 |
| **影子（shadow）** | 远端用户在 Host 上的本地投影账号，不可认证 |
| **单边托管（single-homed）** | 群只存在一份、由一方托管的联邦形态 |
| **三段授权** | 对端认证 + 身份绑定 + 频道授权，缺一即拒 |
| **收/发件箱（inbox/outbox）** | 保证跨实例消息不重不丢的可靠投递模式 |
| **租约（lease）** | 影子身份的有效期，长期无生命周期事件时兜底失效 |
| **fail-closed** | 校验不通过或状态不明时一律拒绝，而非放行 |
